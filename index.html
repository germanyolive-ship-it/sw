Lecture 1
Introduction to Software Engineering
Software Engineering = تطبيق مبادئ هندسية منهجية لتطوير برمجيات موثوقة بكفاءة — مش بس كتابة كود!
ليه SE موجودة؟
بسبب الـ Software Crisis — البرامج كانت بتتأخر وبتتجاوز الميزانية وملانة bugs.

Error vs Fault vs Failure

  • Error: غلطة بشرية من المطور
  • Fault / Bug: الكود المعيب الناتج من الغلطة
  • Failure: لما البرنامج يشتغل ويطلع نتيجة غلط للمستخدم
ترتيب زمني
Error → Fault → Failure
فخ شائع
"Software = Code فقط" — غلط! Software يشمل الـ documentation والـ data وكل المواد المرتبطة.

  • Methods: المنهجية والطريقة (كيف نشتغل)
  • Tools: الأدوات (IDE, UML tools)
  • Process: الإطار اللي بينظم الاثنين

«include» vs «extend» — الفرق الجوهري
«include»: الـ base دايماً يستدعي الـ included (إلزامي). مثال: Withdraw «include» Verify PIN
«extend»: سلوك اختياري. اتجاه السهم: Extension → Base. مثال: Print Receipt «extend» Withdraw

Activity Diagrams
Activity Diagram = رسم بصري يعرض تدفق الأنشطة Sequential وConcurrent معاً. شبه الـ flowchart.
  • ⚫ Initial State: دايرة صغيرة ممتلئة
  • ⊙ Final State: دايرة جوا دايرة
  • ▭ Activity: مستطيل بزوايا مدورة
  • ◇ Decision: ماسة + guards
  • ▬ Fork/Join: خط سميك (concurrent)

Lecture 5 — Part 3
State Machine Diagrams
State Machine = بيمثل دورة حياة كائن واحد من الإنشاء للإنهاء. بيوضح States والـ Transitions بينها.
مثال: User Account
⚫ → New → [isVerified()] → Active → [isSuspendRequested()] → Suspended → [isCancelRequested()] → Closed → ⊙

Lecture 6 — Part 1 🆕
Class Diagrams & Package Diagrams

Class Diagram — الغرض والمكونات

  • يوضح الـ static structure للـ classifiers في النظام
  • بيتكون من: مجموعة classes + مجموعة relationships بينهم
  • مفيد للمطورين وباقي أعضاء الفريق

Class Notation — الشكل

الـ class بتتكوّن من 3 أجزاء:
(1) Class Name — في القسم الأول
(2) Attributes — في القسم الثاني. Type بعد colon
(3) Operations (Methods) — في القسم الثالث. Return type بعد colon
MyClass
+attribute1 : int
-attribute2 : float
#attribute3 : Circle
+op1(in p1 : bool, in p2) : String
-op2(input p3 : int) : float
#op3(out p6) : Class6*

Visibility (Access Modifiers)

+ = public — accessible by any class
- = private — same class only
# = protected — class + subclasses
~ = package — same package only
Access Rightpublic (+)private (-)protected (#)package (~)
Same class✓✓✓✓
Derived classes✓✗✓✓
Any other class✓✗✗same package

Class Relationships (4 أنواع)

Inheritance (Generalization) — "is-a" relationship
خط صلب بـ hollow arrowhead من الـ child للـ parent. الـ abstract class اسمه بـ italics.
مثال: Dog is-a Animal → Subclass1 وSubclass2 من SuperClass
Simple Association — خط صلب بسيط
structural link بين كلاسين. بيبين إن في علاقة بينهم بدون تحديد طبيعتها.
أسماء العلاقات بتتكتب في النص. السهم الصغير بيحدد اتجاه القراءة.
Aggregation — "part-of" (unfilled diamond ◇)
الـ part يمكن يعيش بدون الـ whole. Objects لهم separate lifetimes.
مثال: Computer ◇ — Mainboard, CPU, Memory. الـ CPU يمكن يشتغل منفرد.
Composition — "part-of" (filled diamond ◆)
الـ parts بتتدمر لما الـ whole بيتدمر. Class2 cannot stand by itself.
مثال: Person ◆ — Head, Hand, Leg. الـ Head مش بتعيش بدون Person.

Multiplicity

1Exactly one
0..1Zero or one
*Many (zero or more)
1..*One or more
3..4Exact range
Multiplicity Example
"A Student can take many Courses and many Students can be enrolled in one Course"
→ Student * —takes→ * Course (many-to-many)
Aggregation vs Composition — الفرق الجوهري
Aggregation ◇: الـ parts تعيش مستقلة. لو حذفت الـ whole الـ parts مش هتتحذف.
Composition ◆: الـ parts بتموت مع الـ whole. لو حذفت Person → Head و Hand بتتحذف.
فخ الامتحان
+ = public مش private! كتير بيغلطوا ويقلبوا + و -
❌ "+" = private ✅ "+" = public | ❌ "-" = public ✅ "-" = private

Package Diagrams

Package Diagram = بيوضح ترتيب وتنظيم الـ model elements في المشاريع المتوسطة والكبيرة. بيساعد في تبسيط الـ class diagrams عن طريق تجميع الـ classes في packages.
  • الـ packages بتتمثل كـ file folders بزاوية صغيرة فوق
  • الـ dotted arrows = dependencies بين الـ packages
  • Package names فريدة — لكن classes في packages مختلفة ممكن تتشارك الاسم
«import»
Package1 يستورد وظائف Package2 بالكامل
«access»
Package1 يحتاج مساعدة من Package2
Order Processing System
Packages: UI Framework, Track Order, Order Processing, Shipping
Track Order ↔ Order Processing: «access» dual (بيحتاجوا بعض)
Shipping → Track Order: «import» (بتستورد منه)
UI Framework → Track Order: «access»
Fully Qualified Name
java::util::Date → Owner::Package::Class
Lecture 6 — Part 2 🆕
Sequence Diagrams
Sequence Diagram = Interaction Diagram بيوضح كيف الـ objects بتتفاعل مع بعض عبر الزمن. الـ vertical axis = الوقت. الـ horizontal axis = الـ objects.

أهداف Sequence Diagrams

  • Model high-level interaction between active objects
  • يوضح التفاعل بين objects في سياق الـ use case
  • يعرض التسلسل الزمني للرسائل بين الـ lifelines
  • يدعم Generic (كل المسارات) أو Specific (مسار واحد) interactions

Notation

Actor
Stick figure. خارجي عن الـ subject. يمثل human users, hardware, أو أنظمة خارجية.
Lifeline
مستطيل فوقه خط منقط رأسي. يمثل participant واحد في التفاعل.
Activation
مستطيل رفيع على الـ lifeline. الفترة اللي فيها الـ element بيؤدي operation.
Call Message
خط صلب بسهم. يمثل استدعاء operation على الـ target lifeline.
Return Message
خط منقط بسهم رجعي. يرجع معلومات للـ caller.
Self Message
رسالة للـ lifeline نفسه. loop or recursion داخلي.
Recursive Message
Self message بـ activation جديدة فوق الأولى. يوضح الـ recursion.
Destroy Message
يطلب تدمير lifecycle الـ target lifeline. علامة X في نهاية الـ lifeline.

Combined Fragments (Sequence Fragments)

الـ Combined Fragment = صندوق بيحيط بجزء من التفاعل. في الركن العلوي الأيسر: اسم الـ operator يحدد نوعه.
alt
Alternative — زي الـ if/else. فقط الـ fragment اللي شرطه صح هينفذ.
loop
Loop — بيتنفذ أكتر من مرة. الـ guard بيحدد شرط الاستمرار.
opt
Optional — بيتنفذ بس لو الشرط صح. زي alt بـ trace واحد فقط.
Facebook Auth — Case Study
Lifelines: User، :WebBrowser، :Application، :Facebook Authorization Server، :Facebook Content Server

Basic Flow:
User → WebBrowser: get FB resource
WebBrowser → Application: request FB access
Application → Auth Server: authorize
Auth Server → WebBrowser: permission form
User → WebBrowser: user permission
WebBrowser → Auth Server: process permission

alt fragment:
[permission granted]: Auth Server → Application: FB authorization code → access token → get protected resource ✓
[no permission]: Application → WebBrowser: no authorization → FB resource not available

loop fragment: [for each line item]
opt fragment: [needs confirmation] → 1.3: confirm

Case Study Lab

خطوات مضمونة لحل أي case study في الامتحان

Use Case Recipe

  1. Identify Actors: من بيتعامل مع النظام؟ (بشر أو أنظمة خارجية — بره الـ System Boundary)
  2. Identify Use Cases: النظام بيعمل إيه؟ (أفعال: Withdraw, Login, Register)
  3. Draw System Boundary: مستطيل يحيط بكل الـ use cases
  4. Connect with Associations: كل actor للـ use cases اللي بيتعامل معاها (خط بسيط)
  5. Identify «include»: في use case بيتنادى إلزامياً دايماً من تاني؟
  6. Identify «extend»: في use case اختياري بيضيف وظيفة للـ base؟

Activity Diagram Recipe

  1. حدد الـ Actors / Swimlanes: كل actor له swimlane
  2. ابدأ بـ Initial State ⚫: في أول swimlane — الركن العلوي الأيسر
  3. ارسم الـ Activities: مستطيلات بزوايا مدورة
  4. أضف الـ Decisions ◇: اكتب الـ guard على كل سهم
  5. أضف Fork/Join: لو في concurrent activities
  6. انتهي بـ Final State ⊙

State Machine Recipe

  1. حدد الـ States: الكائن ممكن يكون فيها (New, Active, Suspended, Closed)
  2. ارسم Initial State ⚫
  3. ارسم كل State: مستطيل بزوايا مدورة
  4. حدد الـ Transitions: اكتب event/guard على كل سهم
  5. انتهي بـ Final State ⊙

Class Diagram Recipe

  1. حدد الـ Classes: من السيناريو — الأسماء هي الـ classes
  2. حدد Attributes: الخصائص لكل class مع الـ type والـ visibility
  3. حدد Operations: الوظائف التي تؤديها كل class
  4. حدد الـ Relationships: Inheritance؟ Aggregation؟ Composition؟
  5. أضف Multiplicity: 1، 0..1، *، 1..* على الـ associations
  6. أضف Relationship Names: اسم في منتصف الخط مع سهم الاتجاه
Online Shopping Analysis
Classes: Customer, WebUser, Account, ShoppingCart, Order, Payment, LineItem, Product
Composition: Customer ◆→ Account (Account مش بتعيش بدون Customer)
Aggregation: Account ◇→ ShoppingCart (ShoppingCart ممكن تكون فارغة)
Multiplicity: Customer 1 ←→ 0..1 WebUser | Account 1 ←→ * Order
Visibility: Customer.id = {id} يعني unique identifier

Sequence Diagram Recipe

  1. حدد الـ Actors والـ Objects: من بيشارك في التفاعل؟ (أفقياً من اليسار لليمين)
  2. ارسم الـ Lifelines: مستطيل فوق + خط منقط رأسي لكل participant
  3. حدد الـ Messages: Call أو Return أو Self أو Destroy؟
  4. أضف الـ Activations: مستطيل رفيع على الـ lifeline لكل operation
  5. أضف Combined Fragments: alt لو في conditions، loop لو في تكرار، opt لو اختياري
  6. تأكد من الترتيب الزمني: الرسائل بتنزل من فوق لتحت

🔴 "The system shall be able to manage project schedule."

❌ Not Specific — "manage" غامض (Create? Update? Delete?)
✅ أحسن: "يسمح للمستخدمين بإنشاء وتعديل وحذف مهام المشروع مع تحديد تاريخ بداية ونهاية"

🔴 "The system shall have great usability."

❌ Not Measurable — "great usability" مش بتتقاس بأرقام
✅ أحسن: "95% من المستخدمين الجدد يكملوا الـ checkout في أول محاولة خلال 5 دقائق"

🔴 "The system shall be 100% reliable and 100% available."

❌ Not Achievable — 100% reliability مستحيل تقنياً
✅ أحسن: "99.9% uptime سنوياً مع صيانة مجدولة لا تتجاوز ساعتين شهرياً"
