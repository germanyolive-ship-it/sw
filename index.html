Lecture 1
Introduction to Software Engineering
Software Engineering = تطبيق مبادئ هندسية منهجية (systematic, well-defined scientific principles, techniques, and procedures) لتطوير برمجيات موثوقة بكفاءة.
ليه SE موجودة؟
بسبب الـ Software Crisis — البرامج كانت Late، Over budget، وWith residual faults. أول ما اتقال المصطلح في مؤتمرات NATO سنة 1968 و1969.
Software Product يشمل 3 أشياء:
(1) Programs — الكود
(2) Data structures — البيانات
(3) Documents — وثائق التشغيل والاستخدام

Error vs Fault vs Failure

  • Error (Mistake): غلطة بشرية من المطور — a human action that produces an incorrect result
  • Fault / Bug / Defect: الكود المعيب الناتج من الغلطة — a manifestation of an error in software
  • Failure: لما البرنامج يشتغل ويطلع نتيجة غلط للمستخدم — a deviation of the software from its expected delivery or service
ترتيب زمني
Error → Fault → Failure
فخ شائع
"Software = Code فقط" — غلط! Software = Programs + Data + Documents.
Lecture 2 ⭐
Software Process — 7 Phases
Software Process = a roadmap that helps you create a high quality product, in a timely manner. يتكون من: Methods (HOW TO) + Tools (automated support) + Process (الـ glue)

الـ 7 مراحل

Phase 1 — Requirements (WHAT?)
  • Gathering → Capturing (Data, Functionality, Quality) → Validate via Rapid Prototyping → Deliverable: Requirements document
Phase 2 — Specification (WHAT? — precise)
  • يصف exactly functionality, constraints, inputs, outputs. يجب ألا يكون: Ambiguous، Incomplete، Contradictory
Phase 3 — Design (HOW?)
  • High-level: graphical structure, module interfaces | Detailed: precise module responsibilities, pre/post conditions
Phase 4 — Implementation
  • Implement design in code. Code review + Desk checking (informal by programmer) + SQA testing.
Phase 5 — Integration (in PARALLEL with 4)
  • Correctness + Robustness. Acceptance testing by client. Alpha version → Beta version (corrected alpha).
Phase 6 — Maintenance (67% of total cost!)
Adaptive
Environment changes (OS, DBMS)
Perfective
New/changed user requirements
Corrective
Fix errors found by users
Preventive
Increase future maintainability
Regression Testing
بعد أي maintenance change → اختبر على الـ previous test cases عشان تتأكد إن باقي الـ functionality مش اتأثر.
Phase 7 — Retirement

عندما يصبح البرنامج un-maintainable: drastic design change، new hardware/OS، أو missing/inaccurate documentation. قد يكون الـ rewrite أرخص من التعديل.

أهم فخ
Testing وDocumentation في كل المراحل — مش phase مستقلة في الآخر. Maintenance = 67% من التكلفة!
Lecture 2 — Part 2
SW-CMM — 5 Maturity Levels
SW-CMM (Capability Maturity Model) من SEI / Carnegie Mellon — بيصف كيف تُحسّن الـ Software Process. المنظمة بتتقدم stepwise من 1 لـ 5.
1 — Initial
Ad hoc، chaotic. Depends on current staff. Management = crisis response. معظم المنظمات هنا.
2 — Repeatable
Basic PM. Planning based on previous projects. Measurements for detecting problems.
3 — Defined
Fully documented & standardized. CASE environments applicable. Reviews for quality.
4 — Managed
Detailed measures. Statistical quality controls. Quality & productivity monitored.
5 — Optimizing
Continuous process improvement. Knowledge from each project used in future.
ترتيب لازم تحفظه
Initial → Repeatable → Defined → Managed → Optimizing
فخ
CASE environments بتكون applicable في Level 3 فما فوق — مش في Level 1 أو 2!
Lecture 3 ⭐
Requirements — Functional vs Non-Functional
Requirements Definition = وصف مبسط بلغة عادية للعملاء — understandable without specialized notations
Requirements Specification (SRS) = وثيقة منظمة ودقيقة للمطورين — structured, precise

Functional vs Non-Functional — المقارنة الكاملة

Functional RequirementsNon-Functional Requirements
السؤالWHAT يعمله النظام؟HOW WELL يعمله؟
التعريفProduct features/functions that developers must implementQuality attributes — describe HOW the system performs
محتوىOperations على كل screen، data logic، workflows، reportsPerformance، Scalability، Security، Usability، Reliability
القياسPass/fail — ممكن تختبرها بشكل محددلازم تكون measurable بأرقام
مثال صح ✅"User can log in with email & password""System processes withdrawal in <5 seconds"
مثال غلط ❌لو فيها تفاصيل HOW (implementation details)"The system shall be fast" — مش measurable!
لو فشلواFeature غير متوفرةالنظام يفشل في إرضاء احتياجات المستخدم
أنواع Non-Functional Requirements
Performance، Scalability، Portability، Compatibility، Reliability، Availability، Security، Usability
Functional Requirements يشمل:
Operations on every screen، data handling logic، system reports/outputs، workflows، who can create/modify/delete، regulatory compliance
القاعدة الذهبية للـ Non-Functional
❌ "النظام لازم يكون سريع"
✅ "The system must process cash withdrawal within 5 seconds of bank approval."
❌ "100% reliable" → Not Achievable!
✅ "99.9% uptime annually"

MoSCoW

M — Must Have
Without it → project FAILS. أقصى 60%.
e.g. HR must store leave history
S — Should Have
High priority, NOT essential. Still viable without. أقصى 80%.
e.g. print leave letters
C — Could Have
Nice to have, only if time permits. أقصى 100%.
e.g. send leave notifications
W — Won't Have
Future wishes — next release only.
e.g. remote access — next release
نسب الجهد
Must = أقصى 60% → Must+Should = أقصى 80% → +Could = أقصى 100%
Lecture 4 — Part 2 ⭐
SRS، V&V، RTM، Sign-off
SRS = detailed description of a software system with its functional and non-functional requirements. Developed based on agreement between customer and contractors.

Users of SRS:

Customers
يحددوا ويراجعوا المتطلبات
Managers
يخططوا للـ bid والتطوير
System Engineers
يفهموا إيه اللي هيتبنى
Test Engineers
يبنوا validation tests
Maintenance Eng.
يفهموا علاقات النظام
Verification = "Are we building the thing right?" — evaluating intermediary work products
Validation = "Are we building the right thing?" — evaluating the final product
VerificationValidation
السؤالBuilding it right?Building the right thing?
التوقيتIntermediary (أثناء)Final product
الأنشطةReviews، meetings، inspectionsSmoke، functional، regression testing
RTM (Requirements Traceability Matrix) = document that establishes and tracks relationships between requirements and other artifacts throughout lifecycle.

5 Benefits of RTM:

  • (1) Management of solution scope: evaluate value, prioritize, avoid scope creep
  • (2) Quick evaluation of changes: identify related objectives, easy identification of failed test cases
  • (3) Reduced project risk: identify critical dependencies, better visibility
  • (4) Promotes consistency: detect if two terms refer to same entity (Client vs Registered Customer)
  • (5) Lifecycle monitoring: track which requirements are validated, pending, rejected
Sign-off = stakeholders agree and approve requirements. بعده أي تعديل له تكلفة إضافية!
فخ
Test Engineers بيستخدموا الـ SRS لـ validation tests — مش bid planning (ده الـ Managers)!
Lecture 5 — Part 1
UML — Use Case Diagrams
UML = Unified Modeling Language — لغة نمذجة بصرية موحدة. مش لغة برمجة!

ليه نستخدم UML؟

  • Detect errors early (before coding)
  • Communicate design to stakeholders
  • Provide documentation
  • Reduce complexity through visual abstraction

UML Diagram Classification — مهم MCQ!

Structure Diagrams
Class، Component، Deployment، Package
الـ static structure
Behaviour Diagrams
Use Case، Activity، State Machine
الـ dynamic behavior
Interaction Diagrams
Sequence، Collaboration، Timing
التفاعل بين الكائنات
«include» vs «extend» — الفرق الجوهري
«include»: إلزامي دايماً. Arrow: Base → Included. مثال: Withdraw «include» Verify PIN

«extend»: اختياري/شرطي. Arrow: Extension → Base. مثال: Print Receipt «extend» Withdraw
Use Case Mistakes الشائعة
❌ Actors جوا الـ System Boundary → ✅ بره دايماً
❌ سهم «extend» من Base للـ Extension → ✅ من Extension للـ Base
❌ Include = optional → ✅ Include = mandatory دايماً
❌ System Functions تُكتب في الـ Actors → ✅ في الـ Use Case ovals

Requirements Engineering — Deep Dive

الجزء ده كان "سطحي" في النسخة القديمة — تم توسيعه بالكامل

الـ 3 مراحل الرئيسية لـ Requirements Engineering

(1) Requirements Elicitation
Discover، reveal، articulate، and understand the requirements of the system from stakeholders.

المشكلة: الـ stakeholders غالباً مش عارفين exactly إيه اللي هم عايزينه — مش من باب الإهمال، لكن لصعوبة التعبير عن الاحتياجات!

Output: Raw requirements لم يتم تحليلها بعد

(2) Requirements Analysis & Negotiation
Examine requirements for conflicts، inconsistencies، missing elements. Combine related. Negotiate with stakeholders.

الأنشطة:

  • Identify conflicts between requirements from different stakeholders
  • Identify inconsistencies in the same requirement
  • Combine related requirements that belong together
  • Identify missing requirements
  • Negotiate trade-offs with stakeholders

Output: Consistent، conflict-free، complete requirements

(3) Requirements Specification
Record requirements in a form that can be reviewed and agreed upon. Can be: Natural Language، Formal Notation، or Graphical Representations.

Formats:

Natural Language — قابل للجميع لكن ambiguous
Formal Notation — precise لكن خبراء فقط يفهموه
Graphical (UML) — visual، شامل

Output: SRS Document → Sign-off

ترتيب مهم جداً
Elicitation → Analysis & Negotiation → Specification → SRS → Sign-off. الترتيب ده لازم تحفظه!

Elicitation Techniques — المقارنة الكاملة (مهم MCQ)

#1 Prototyping

إيه هو؟ بناء نموذج مبكر للنظام عشان العميل يشوفه ويقيّمه

متى نستخدمه؟ لما المتطلبات غامضة، أو العميل مش عارف هو عايز إيه بالظبط

✅ Benefit: Verify design while still time to change it
✅ Helps detect misunderstandings early
⚠️ قد يأخذ وقت وموارد لبناء الـ prototype
⚠️ قد يعتقد العميل إن الـ prototype = النظام الحقيقي
#2 Workshops

إيه هو؟ Focused event مع key stakeholders — structured facilitated meeting

متى نستخدمه؟ لما عايزين نوصل لـ agreement سريع بين أطراف متعددة

✅ Benefit: Basic requirements done quickly
✅ يكشف conflicts بين stakeholders
⚠️ خطر: شخصية مسيطرة (dominant personality) تطغى على البقية
⚠️ Do NOT involve too many participants → slow down
#3 Interviews

إيه هو؟ One-on-one sessions مع stakeholders محددين

متى نستخدمه؟ لما عايزين فهم عميق لـ specific domain أو user

✅ Benefit: Understand real (not just perceived) need
✅ بيساعد في كشف الـ tacit knowledge
⚠️ وقت طويل نسبياً
⚠️ البيانات قد تكون مش representative
#4 Surveys / Questionnaires

نوعين: Fixed Format (predefined answers) | Free Format (open response)

متى نستخدمه؟ لما في عدد كبير من المستخدمين أو جغرافياً بعيدين

✅ يوصل لعدد كبير من الناس بسرعة
✅ تكلفة أقل من الـ interviews
⚠️ مش بيسمح بـ follow-up questions
⚠️ نسبة الرد قد تكون منخفضة
#5 Observation

إيه هو؟ مراقبة المستخدمين وهم بيشتغلوا في بيئتهم الفعلية

متى نستخدمه؟ لما نحتاج نفهم الـ actual workflow — مش اللي المستخدم بيقوله

✅ غني جداً بالمعلومات الحقيقية
✅ يكشف الـ implicit requirements
⚠️ Users adjust behavior when being watched!
⚠️ وقت كتير لتحليل النتائج
فخ شائع في MCQ
Fixed Format Survey = answers محددة مسبقاً (اختر من). Free Format = open-ended (اكتب رأيك).
Observation يكشف الحقيقة لكن users بيغيروا سلوكهم لما يعرفوا إنهم بيتراقبوا!

Elicitation Process — 4 Steps

Step 1 — Choose optimal approach
Based on: organization makeup، political climate، project nature، personal strengths. No single technique works for all projects!
Step 2 — Preparation
Establish: objective، specific participants، resources، predetermined questions + how to record answers، agenda with start/end times.
Step 3 — Conduct (4 stages)
Introduction: Set stage، tone، discuss activities/timing
Body: Execute technique (interviews→questions، workshops→group activity)
Close: Closing questions ("any info we didn't cover?")، ask if open to follow-up
Follow-up: Clarify، verify accuracy of recorded info
Step 4 — Analyze Results
Reading notes → summarize → identify keywords/ideas. Tools: QVscribe، NVivo

ليه الـ Requirements بتبقى بايظة؟ — 5 Difficulties

(1) Articulation Problems
Users: قد لا يعرفوا احتياجاتهم، أو خايفين يعبروا عنها. Developers: قد لا يستمعوا جيداً أو يتجاوزوا آراء المستخدمين.
(2) Communication Barriers
Users ومطورين بيتكلموا different vocabularies — المستخدم بيقول "process the order" والمطور بيفهم حاجة تانية.
(3) Knowledge & Cognitive Limitations
الـ elicitor لازم يكون عنده domain knowledge. الناس بتصيغ المشكلة في صورة الحل المفضل لديهم.
(4) Human Behavior Issues
خوف إن البرنامج هيغير في طريقة الشغل أو يسبب فقدان وظائف → بيقاوموا أو بيخفوا معلومات.
(5) Technical Issues
المتطلبات بتتغير مع الوقت. التكنولوجيا بتتغير بسرعة. ده بيخلي Requirements stale بسرعة.

Use Case Recipe

  1. Identify Actors: من بيتعامل مع النظام؟ (بشر أو أنظمة — بره الـ System Boundary)
  2. Identify Use Cases: النظام بيعمل إيه؟ (أفعال: Withdraw، Login)
  3. Draw System Boundary: مستطيل يحيط بكل الـ use cases
  4. Connect Associations: خط بسيط بين كل actor والـ use cases بتاعته
  5. Identify «include»: use case بيتنادى إلزامياً من تاني؟
  6. Identify «extend»: use case اختياري بيضيف وظيفة للـ base؟

Activity Diagram Recipe

  1. حدد الـ Actors / Swimlanes
  2. ابدأ بـ Initial State ⚫: في الركن العلوي الأيسر
  3. ارسم الـ Activities: مستطيلات بزوايا مدورة
  4. أضف الـ Decisions ◇: اكتب الـ guard على كل سهم
  5. أضف Fork/Join: للـ concurrent activities
  6. انتهي بـ Final State ⊙

State Machine Recipe

  1. حدد الـ States: الكائن ممكن يكون فيها
  2. ارسم Initial State ⚫
  3. ارسم كل State: مستطيل بزوايا مدورة
  4. حدد الـ Transitions: اكتب event/guard على كل سهم
  5. انتهي بـ Final State ⊙

Class Diagram Recipe

  1. حدد الـ Classes: الأسماء من السيناريو
  2. حدد Attributes: مع type والـ visibility (+/-/#/~)
  3. حدد Operations: الوظائف
  4. حدد الـ Relationships: Inheritance/Aggregation/Composition؟
  5. أضف Multiplicity: 1، 0..1، *، 1..*
  6. أضف Relationship Names: في منتصف الخط

Sequence Diagram Recipe

  1. حدد الـ Actors والـ Objects: أفقياً من اليسار
  2. ارسم الـ Lifelines: مستطيل فوق + خط منقط رأسي
  3. حدد الـ Messages: Call (solid→) أو Return (dashed←) أو Self أو Destroy
  4. أضف الـ Activations: مستطيل رفيع على الـ lifeline
  5. أضف Combined Fragments: alt/loop/opt
  6. تأكد من الترتيب الزمني: من فوق لتحت

❌ Not Specific — "manage" غامض (Create? Update? Delete?)

❌ Not Measurable — "great usability" مش بتتقاس
✅ "95% من المستخدمين يكملوا checkout في 5 دقائق"

🔴 "The system shall be 100% reliable and 100% available."

❌ Not Achievable — 100% مستحيل
✅ "99.9% uptime annually مع صيانة ≤ ساعتين/شهر"

Requirements Engineering Analysis

Scenario: "The bank needs a system for ATM withdrawals."

  1. Elicitation: Interview bank staff. Observe current ATM usage. Workshop with managers. Survey customers on pain points.
  2. Functional Requirements: User can withdraw cash. User can check balance. System verifies PIN. System logs transaction.
  3. Non-Functional: System processes withdrawal in <5 seconds. 99.9% uptime. Supports 1000 concurrent transactions.
  4. Analysis: Check conflicts — does "check balance" include mini-statement? Negotiate with stakeholders.
  5. SMART Check: Remove vague words. Add measurements to all NFRs.
  6. MoSCoW: Must: PIN verification، withdrawal | Should: balance inquiry | Could: mini-statement | Won't: investment services
  7. SRS + RTM: Document everything. Trace each requirement to test cases.
  8. Sign-off: Get stakeholder approval.
