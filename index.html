Lecture 1
Introduction to Software Engineering
Software Engineering = تطبيق مبادئ هندسية منهجية (systematic, well-defined scientific principles, techniques, and procedures) لتطوير برمجيات موثوقة بكفاءة.
ليه SE موجودة؟
بسبب الـ Software Crisis — البرامج كانت بتتأخر (Late)، تتجاوز الميزانية (Over budget)، وملانة (With residual faults). أول ما اتقال المصطلح في مؤتمرات NATO سنة 1968 و1969.
Software Product يشمل 3 أشياء:
(1) Programs — الكود اللي بيتنفذ
(2) Data structures — البيانات المصاحبة
(3) Documents — وثائق التشغيل والاستخدام

Error vs Fault vs Failure

  • Error (Mistake): غلطة بشرية من المطور — a human action that produces an incorrect result
  • Fault / Bug / Defect: الكود المعيب الناتج من الغلطة — a manifestation of an error in software
  • Failure: لما البرنامج يشتغل ويطلع نتيجة غلط للمستخدم — a deviation of the software from its expected delivery or service
ترتيب زمني
Error → Fault → Failure
فخ شائع
"Software = Code فقط" — غلط! Software = Programs + Data + Documents.
Lecture 2 ⭐
Software Process — 7 Phases
Software Process = a roadmap that helps you create a high quality product, in a timely manner.
يتكون من: Methods (HOW TO) + Tools (automated support) + Process (الـ glue اللي بيربطهم)

الـ 7 مراحل

Phase 1 — Requirements Phase (WHAT?)
  • (1) Requirements Gathering: تفهم العميل عايز إيه
  • (2) Requirements Capturing: Data، Functionality، Quality Attributes
  • (3) Validate Requirements: عن طريق Rapid Prototyping
  • (4) Deliverable: Requirements document — checked by client, users, dev team
Phase 2 — Specification Phase (WHAT? — precise)

الـ Specifications document: بتوصف exactly functionality، constraints، inputs، outputs

لازم مش تكون:

  • Ambiguous: open to more than one interpretation
  • Incomplete: missing necessary parts
  • Contradictory: mutually opposed or inconsistent
SQA role: Check for contradictions/ambiguities/incompleteness، ensure feasibility، trace every spec back to requirements، review by SQA + specification team + client
Phase 3 — Design Phase (HOW?)
  • High-level Design: graphical structure، module interfaces، algorithms overview، non-functional constraints
  • Detailed Design (Low-level): precise module responsibilities، pre/post conditions، invariants، internal data structures
SQA role: Check for logic faults، interface faults، lack of exception handling، nonconformance to spec. Documentation: architecture + detailed design
Phase 4 — Implementation Phase
  • Implement the detailed design in code
  • Testing: Code review + Running test cases
  • Desk checking: informal testing by the programmer
  • Testing by SQA group
Documentation: Source code with comments + test cases
Phase 5 — Integration Phase (in parallel with 4)
  • Integrate modules — in parallel with implementation
  • Correctness: free from error | Robustness: works under invalid inputs/stressful conditions
  • Acceptance testing by client: accept or reject the delivered software
  • Selected users test on site → Alpha version
  • Corrected alpha → Beta version
Documentation: commented source code، test cases، User/Operator/Database manuals
Phase 6 — Maintenance Phase (67% of total cost!)
Adaptive
Modifying to cope with changes in environment (OS, DBMS)
Perfective
Implementing new or changed user requirements (functional enhancements)
Corrective
Diagnosing and fixing errors found by users
Preventive
Increasing maintainability/reliability to prevent future problems
Regression Testing
بعد أي تعديل في الـ Maintenance، لازم تختبر المنتج على الـ previous test cases عشان تتأكد إن باقي الـ functionality مش اتأثر.
Phase 7 — Retirement

Software becomes un-maintainable when:

  • A drastic change in design is proposed
  • Must be implemented on totally new hardware/OS
  • Documentation is missing or inaccurate

→ It may be cheaper to rewrite from scratch than to modify it

أهم فخ في الـ Process
Testing و Documentation مش مرحلة في الآخر — بيحصلوا في كل المراحل. والـ Maintenance = 67% من إجمالي تكلفة المشروع!
Lecture 2 — Part 2
SW-CMM — 5 Maturity Levels
SW-CMM (Capability Maturity Model) = نموذج من الـ SEI / Carnegie Mellon بيوصف كيف تحسين الـ Software Process. المنظمة بتتقدم stepwise من level 1 لـ 5.
Level 1 — Initial
Ad hoc (occasionally chaotic). Depends totally on current staff. Entire process unpredictable. Management = crisis response.
← Most organizations are here!
Level 2 — Repeatable
Basic project management to track cost، schedule، functionality. Planning based on similar previous projects. Measurements for detecting problems.
Level 3 — Defined
Process fully documented & standardized. Reviews for quality improvement. CASE environments applicable.
Level 4 — Managed
Detailed measures of product & process quality collected. Statistical quality controls in place. Quality & productivity continually monitored.
Level 5 — Optimizing
Continuous process improvement. Knowledge from each project used in future. Statistical quality & process controls.
ترتيب المستويات
Initial → Repeatable → Defined → Managed → Optimizing
من المحاضرة
يستغرق 3-5 سنين للانتقال من Level 1 لـ 2، و1.5-3 سنين من 2 لـ 3. معظم المنظمات لسه في Level 1.
هناك أيضاً: ISO 9000 (مطلوب للتعامل مع الـ EU) و ISO/IEC 15504 (SPICE)
فخ
CASE environments بتكون applicable في Level 3 فما فوق — مش في Level 1 أو 2!
Lecture 3 ⭐
Requirements Engineering — Part 1
Requirements Definition = وصف مبسط بلغة عادية للعملاء — understandable by customers without specialized notations
Requirements Specification (SRS) = وثيقة منظمة ودقيقة للمطورين — structured document setting out system services in detail; must be precise

Functional Requirements (WHAT)

Product features or functions that developers must implement to enable users to accomplish their tasks.
لا تحتوي HOW — design/implementation details مش من هنا.
Functional Requirements should include:
Details of operations on every screen، data handling logic، system reports/outputs، workflows، who can create/modify/delete data، regulatory compliance

Non-Functional Requirements (HOW WELL)

بتوصف كيف يؤدي النظام وظيفته. تُعرف بـ quality attributes. لازم تكون قابلة للقياس. Failing to meet them → system fails to satisfy user needs.
أنواع NFR
Performance، Scalability، Portability، Compatibility، Reliability، Availability، Security، Usability
القاعدة الذهبية
❌ "النظام لازم يكون سريع"
✅ "The system must process cash withdrawal within 5 seconds of bank approval."

Requirements Engineering Process — 3 مراحل رئيسية

  • (1) Requirements Elicitation: discover, reveal, articulate, understand requirements
  • (2) Requirements Analysis & Negotiation: examine for conflicts, inconsistencies, combine related, identify missing
  • (3) Requirements Specification: record requirements in natural language / formal / graphical representations

Top 5 Elicitation Techniques

#1 Prototyping — بناء نموذج مبكر. Benefit: verify design while still time to change it
#2 Workshops — focused event مع key stakeholders. Benefit: basic requirements done quickly. خطر: شخصية مسيطرة
#3 Interviews — one-on-one. Benefit: understand real (not just perceived) need
#4 Surveys / Questionnaires — Fixed Format (predefined answers) أو Free Format (open response)
#5 Observation — مراقبة المستخدمين في عملهم. غني لكن users tend to adjust behavior when watched
Lecture 3 — Part 2 🆕
Elicitation Process & Difficulties

Elicitation Process — 4 Steps

Step 1 — Choose the optimal elicitation approach
Based on: organization makeup، political climate، project nature، personal strengths/preferences. No single technique works for all projects!
Step 2 — Elicitation Preparation
You should establish: objective for activities، specific participants، resources/supporting materials، predetermined questions + how to record answers، agenda with start/end times
Step 3 — Conduct the Elicitation (4 stages)
1. Introduction: set stage، establish tone، discuss activities/timing
2. Body: execute chosen technique (interviews → questions، workshops → group activity)
3. Close: closing questions ("any info we didn't cover?")، ask if open to follow-up
4. Follow-up: clarify، verify accuracy of recorded info
Step 4 — Analyze Elicitation Results
Reading notes → summarize → identify keywords/ideas. Tools: QVscribe، NVivo

Difficulties of Requirements Elicitation (5 أنواع)

(1) Articulation Problems
Users: may not be aware of needs، unable/afraid to articulate them
Developers: may not really listen، tend to overrule users
(2) Communication Barriers
Users and developers have different professional vocabularies
(3) Knowledge & Cognitive Limitations
Elicitor must have adequate domain knowledge. People tend to state the problem in terms of the favored solution
(4) Human Behavior Issues
Fear that software will necessitate changes in behavior، including potential loss of jobs
(5) Technical Issues
Requirements change over time. Software/hardware technologies are changing rapidly

SMART Criteria

بلا غموض، consistent terminology
M
Measurable
فيه رقم — especially for NFR
A
Achievable
ممكن تنفيذه في حدود المعرفة البشرية

realistic given the resources

SMART Examples from lecture
❌ "The system shall manage project schedule." → Not Specific (Manage = Create/Update/Delete?)
❌ "The system shall have great usability." → Not Measurable
❌ "100% reliable and 100% available" → Not Achievable
❌ "Implement Oracle in 1 month" → Not Relevant (ERPs take 3+ months)

MoSCoW

M — Must Have
Necessity — without it the project FAILS. No alternative. أقصى 60%
e.g. HR system must store employee leave history
S — Should Have
High priority but NOT essential. Project still viable without it. أقصى 80%
e.g. should allow printing leave letters
C — Could Have
Nice to have — only if more than enough time. أقصى 100%
e.g. could send notifications on pending leave
W — Won't Have
Future wishes — next release only
e.g. won't support remote access — may in next release
نسب الجهد
Must = أقصى 60% → Must+Should = أقصى 80% → +Could = أقصى 100%
Lecture 4 — Part 2 ⭐
SRS، V&V، RTM، Sign-off
SRS = detailed description of a software system to be developed with its functional and non-functional requirements. Developed based on the agreement between customer and contractors.

Users of SRS:

Customers
يحددوا ويراجعوا المتطلبات
Managers
يخططوا للـ bid والتطوير
System Engineers
يفهموا إيه اللي هيتبنى
Test Engineers
يبنوا validation tests للنظام
Maintenance Eng.
يفهموا علاقات النظام
Verification = evaluating intermediary work products — "Are we building the thing right?"
Validation = evaluating the final product — "Are we building the right thing?"
VerificationValidation السؤالBuilding it right?Building the right thing? التوقيتIntermediary (أثناء التطوير)Final product الأنشطةReviews، meetings، inspectionsSmoke، functional، regression، systems testing
RTM (Requirements Traceability Matrix) = document that establishes and tracks relationships between requirements and other artifacts throughout the project lifecycle.

5 Benefits of RTM:

  • (1) Management of solution scope: evaluate value of each requirement، prioritize، avoid scope creep
  • (2) Quick evaluation of potential changes: identify related objectives، easy identification of failed test case requirements
  • (3) Reduced project risk: identify critical dependencies، better visibility and control
  • (4) Promotes consistency: detect if two terms refer to same entity (e.g. Client vs Registered Customer)
  • (5) Lifecycle monitoring & control: track which requirements are validated، pending، rejected، and which correspond to a specific release
Sign-off = indication that stakeholders agree with and approve requirements. بعده أي تعديل له تكلفة إضافية!
فخ
Test Engineers بيستخدموا الـ SRS لـ validation tests — مش للـ bid planning. الـ bid planning = Managers!
Lecture 5 — Part 1
UML — Use Case Diagrams
UML = Unified Modeling Language — لغة نمذجة بصرية موحدة. مش لغة برمجة!
Structure Diagrams
Class، Component، Deployment، Package
Behaviour Diagrams
Use Case، Activity، State Machine
Interaction Diagrams
Sequence، Collaboration، Timing
«include» vs «extend» — الفرق الجوهري
«include»: الـ base دايماً يستدعي الـ included (إلزامي). Arrow: Base → Included
مثال: Withdraw «include» Verify PIN

«extend»: سلوك اختياري/شرطي. Arrow: Extension → Base
مثال: Print Receipt «extend» Withdraw
فخاخ
Actors دايماً بره الـ System Boundary — مش جوا!
سهم «extend» من الـ Extension للـ Base — مش العكس!

Activity Diagram = رسم بصري يعرض تدفق الأنشطة Sequential وConcurrent معاً. شبه الـ flowchart.
  • ⚫ Initial State: دايرة صغيرة ممتلئة
  • ⊙ Final State: دايرة جوا دايرة
  • ▭ Activity: مستطيل بزوايا مدورة
  • ◇ Decision: ماسة + guards على الأسهم
  • ▬ Fork/Join: خط أسود سميك (concurrent flows)

Lecture 5 — Part 3
State Machine Diagrams
State Machine = بيمثل دورة حياة كائن واحد من الإنشاء للإنهاء. بيوضح States والـ Transitions بينها.
مثال: User Account

Lecture 6 — Part 1 🆕
Class Diagrams & Package Diagrams

Class Diagram — Overview

بيوضح الـ static structure للـ classifiers في النظام. بيتكون من classes + relationships. مفيد للمطورين وكل الفريق.

Class Notation

3 أقسام: (1) Class Name | (2) Attributes: name: type | (3) Operations: name(params): returnType
MyClass
+attribute1 : int
-attribute2 : float
#attribute3 : Circle
+op1(in p1 : bool) : String
-op2(in p3 : int) : float
#op3(out p6) : Class6*

Visibility (Access Modifiers)

+ = public — accessible by any class
- = private — same class only
# = protected — class + subclasses
~ = package — same package only
Access Rightpublic (+)private (-)protected (#)package (~)
Same class✓✓✓✓
Derived classes✓✗✓✓
Any other class✓✗✗same package

Class Relationships (4 أنواع)

Inheritance (Generalization) — "is-a"
Solid line + hollow arrowhead من الـ child للـ parent. Abstract class بـ italics.
Simple Association — structural link
Plain solid line بين كلاسين. اسم العلاقة في المنتصف. سهم صغير لاتجاه القراءة.
Aggregation ◇ — "part-of" مع استقلالية
Unfilled diamond. Objects have separate lifetimes. مثال: Computer ◇— CPU (الـ CPU يعيش بدون Computer)
Composition ◆ — "part-of" بدون استقلالية
Filled diamond. Parts die with whole. مثال: Person ◆— Head (الـ Head مش تعيش بدون Person)

Multiplicity

1Exactly one
0..1Zero or one
*Many (zero or more)
1..*One or more
3..4Exact range
فخ الامتحان
+ = public مش private! كتير بيغلطوا ويقلبوا + و -
Inheritance = hollow arrowhead — مش filled!
Composition ◆ filled diamond — Aggregation ◇ unfilled diamond

Package Diagrams

Package Diagram = organizes model elements into groups (packages) to simplify complex class diagrams. مفيد في المشاريع المتوسطة والكبيرة.
  • Packages = file folders (مستطيل بزاوية صغيرة فوق)
  • Dotted arrows = dependencies بين packages
  • Package names لازم unique في النظام
  • Classes في packages مختلفة ممكن تتشارك نفس الاسم
«import»
Package imports the functionality of another package
«access»
Package requires help from functions of another package
Fully Qualified Name
java::util::Date → Owner::Package::Class
Lecture 6 — Part 2 🆕
Sequence Diagrams
Sequence Diagram = Interaction Diagram بيوضح كيف الـ objects بتتفاعل عبر الزمن. Vertical axis = الوقت (هبوطاً). Horizontal axis = الـ objects/participants.

Notation

Actor
Stick figure. External entity (human، hardware، or external system)
Lifeline
مستطيل فوق + خط منقط رأسي. Represents an individual participant
Activation
مستطيل رفيع على الـ lifeline. Period during which an element is performing an operation
Call Message
Solid line + filled arrow. Invocation of an operation on target lifeline
Return Message
Dashed line + open arrow. Pass information back to the caller
Self Message
Arrow back to same lifeline. Internal call or loop
Recursive Message
Self message + new activation on top of existing one. Shows recursion
Destroy Message
Message + X mark. Terminates the lifecycle of target lifeline

Combined Fragments

alt
Alternative — if/else. Only the trace whose condition is true executes.
loop
Loop — executes multiple times based on guard condition.
opt
Optional — equivalent to alt with only one trace.
فخاخ Sequence Diagram
❌ Return Message = خط صلب — ✅ Return Message = خط منقط
❌ Time axis = أفقي — ✅ Time axis = رأسي هبوطاً
❌ Fragment operator في الركن العلوي الأيمن — ✅ في الركن العلوي الأيسر

Case Study Lab

خطوات مضمونة لحل أي case study في الامتحان

Use Case Recipe

  1. Identify Actors: من بيتعامل مع النظام؟ (بشر أو أنظمة خارجية — بره الـ System Boundary)
  2. Identify Use Cases: النظام بيعمل إيه؟ (أفعال: Withdraw، Login، Register)
  3. Draw System Boundary: مستطيل يحيط بكل الـ use cases
  4. Connect with Associations: كل actor للـ use cases اللي بيتعامل معاها (خط بسيط)
  5. Identify «include»: في use case بيتنادى إلزامياً دايماً من تاني؟
  6. Identify «extend»: في use case اختياري بيضيف وظيفة للـ base؟

Activity Diagram Recipe

  1. حدد الـ Actors / Swimlanes: كل actor له swimlane
  2. ابدأ بـ Initial State ⚫: في أول swimlane — الركن العلوي الأيسر
  3. ارسم الـ Activities: مستطيلات بزوايا مدورة
  4. أضف الـ Decisions ◇: اكتب الـ guard على كل سهم
  5. أضف Fork/Join: لو في concurrent activities
  6. انتهي بـ Final State ⊙

State Machine Recipe

  1. حدد الـ States: الكائن ممكن يكون فيها (New، Active، Suspended، Closed)
  2. ارسم Initial State ⚫
  3. ارسم كل State: مستطيل بزوايا مدورة
  4. حدد الـ Transitions: اكتب event/guard على كل سهم
  5. انتهي بـ Final State ⊙

Class Diagram Recipe

  1. حدد الـ Classes: من السيناريو — الأسماء هي الـ classes
  2. حدد Attributes: الخصائص لكل class مع الـ type والـ visibility
  3. حدد Operations: الوظائف التي تؤديها كل class
  4. حدد الـ Relationships: Inheritance؟ Aggregation؟ Composition؟
  5. أضف Multiplicity: 1، 0..1، *، 1..* على الـ associations
  6. أضف Relationship Names: اسم في منتصف الخط مع سهم الاتجاه

Sequence Diagram Recipe

  1. حدد الـ Actors والـ Objects: من بيشارك في التفاعل؟ (أفقياً من اليسار لليمين)
  2. ارسم الـ Lifelines: مستطيل فوق + خط منقط رأسي لكل participant
  3. حدد الـ Messages: Call أو Return أو Self أو Destroy؟
  4. أضف الـ Activations: مستطيل رفيع على الـ lifeline لكل operation
  5. أضف Combined Fragments: alt لو في conditions، loop لو في تكرار، opt لو اختياري
  6. تأكد من الترتيب الزمني: الرسائل بتنزل من فوق لتحت
